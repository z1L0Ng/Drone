\section{Evaluation}
\label{sec:evaluation}

The evaluation follows the same layered structure as the system. First, we evaluate whether the acoustic recognizer separates emergency, movement, and unknown speech under rotor-noisy conditions. Second, we measure how that behavior changes as the acoustic setting becomes harder. Third, we test whether the embedded prototype can produce and report one intent event per one-second audio window. Fourth, we compare the recognizer with compact speech baselines under matched conditions. Finally, we evaluate whether the control boundary handles events according to the safety-state contract and whether people can use the interaction naturally in controlled studies.

This organization keeps each measurement tied to the claim it can support. Offline acoustic tests establish whether the intent-event abstraction is learnable. Rotor-noise and speaker-geometry tests show how stable that abstraction is when the physical setting changes. Embedded runtime measurements show whether the event source can run near the drone. Control-boundary tests show whether events remain mediated. User studies and demonstrations connect the technical pipeline back to the interaction that motivates the system.

\subsection{Offline Recognition Quality}

The first evaluation isolates the acoustic recognizer from the embedded runtime and the control bridge. The setup uses the paper's rotor-noisy test condition with three intent events: emergency, movement, and unknown. We report accuracy, macro F1, and per-class precision, recall, and F1. Emergency is reported separately because it is safety-critical. Macro F1 is reported because movement and unknown should not be hidden by a single aggregate score.

The offline acoustic reference model reaches 88\% accuracy and 0.88 macro F1 under the noisy test condition, with emergency precision, recall, and F1 of 0.96, 0.79, and 0.87. The embedded recognizer used in the ESP32 prototype reaches 84.8\% accuracy and 0.85 macro F1, with emergency precision, recall, and F1 of 0.95, 0.70, and 0.81. This gap is expected: the embedded model is constrained by integer inference and microcontroller runtime, while the reference model is used to characterize the stronger acoustic design.

The interpretation is that \sys{} has a measurable acoustic separation point, but the embedded recognizer pays a recall cost for deployment. For a safety interaction layer, that cost matters more than a single accuracy number. Threshold sweeps complete this picture by showing the trade-off between emergency recall and unknown containment.

The offline analysis also needs a confusion matrix and per-class error discussion. Two errors are especially important. First, emergency speech classified as movement or unknown reduces the usefulness of the safety channel. Second, unknown speech classified as movement or emergency creates pressure on the control boundary. Reporting these errors separately connects model behavior to the event semantics in Section~\ref{sec:system}.

\subsection{Robustness Under Rotor Noise}

The second evaluation measures how recognition changes as rotor noise and speaking geometry vary. The motivation is simple: a nearby UAV is not a static acoustic source. Rotor speed, drone orientation, microphone placement, and speaker distance can all change the mixture reaching the microphone. A single noisy-set score cannot show whether the recognizer degrades smoothly or fails under particular conditions.

The setup compares the same recognizer across clean speech, mixed rotor-noise conditions, and recorded or live rotor-playback conditions. Each condition uses the same label mapping and reports the same metrics: accuracy, macro F1, emergency recall, movement recall, and the rate at which unknown audio is incorrectly turned into emergency or movement. The robustness curve also records the noise source, mixing rule or measured level, distance, and microphone placement.

A weak result identifies the acoustic conditions where the safety interaction layer needs shielding, better placement, a stronger frontend, or more conservative thresholds.

The same experiment can also compare frontend choices. Log-mel, MFCC, and normalized energy frontends may respond differently to rotor harmonics and loudness changes. The useful comparison is not only which frontend maximizes average accuracy, but which frontend preserves emergency recall while keeping unknown false events low. This is why the robustness table reports safety-facing metrics rather than only a single recognition score.

\subsection{Embedded Inference and Event Reporting}

The third evaluation measures whether the event source can run on the ESP32 prototype and report intent events to the safety-state bridge. Figure~\ref{fig:response_time_breakdown} separates the full timing path into capture, feature extraction, integer model invocation, event reporting, bridge decision, command gating, Tello SDK dispatch, and acknowledgement or timeout. These stages answer different questions. Model invocation measures the board-side recognizer kernel. Event-reporting timing measures whether the bridge receives a stable event stream. Bridge and SDK timing measure how quickly a received event can be mediated before any command boundary is reached.

The integer model invocation takes 627 ms on the ESP32 prototype. The first board event appears after 1606 ms because the first one-second audio window must be captured before feature extraction and inference can complete. Once the pipeline is running, the prototype sustains a steady event period with 95th-percentile spacing of 1005 ms. In a continuous event-reporting test, all 30 one-second windows were delivered to the bridge, with median and 95th-percentile inter-arrival times of 990 ms and 1021 ms. A grounded SDK reachability probe produced no acknowledgement and timed out after 3002 ms, so command-boundary timing remains a separate constraint rather than a completed fast-response result.

The key distinction is between board-side inference, event reporting, and control response. A fast model invocation does not guarantee that the bridge receives events at a stable cadence. Stable event reporting does not guarantee that the Tello SDK boundary has been reached or acknowledged. The evaluation therefore keeps these measurements separate instead of collapsing them into one response-time number.

\subsection{Baseline Comparison}

The fourth evaluation compares \sys{} against compact speech models under the same task definition. The comparison is not meant to show that a larger speech architecture is universally better. It asks whether the proposed recognizer provides a better balance of noisy recognition quality, emergency recall, unknown containment, and embedded feasibility for the UAV safety interaction layer.

The intended setup includes compact keyword-spotting or command-recognition baselines under a common train/test split, frontend budget, label mapping, and noisy evaluation condition. Each baseline reports accuracy, macro F1, emergency recall, unknown false event rate, model size, and whether the converted model can run on the embedded path. The current preliminary offline baseline rows use the same three-event target and log-mel frontend, while exact split and support parity remain to be finalized before the final leaderboard.

The interpretation combines acoustic quality and deployability. A baseline that is accurate offline but cannot be converted to the embedded path does not satisfy the system goal. A baseline that runs quickly but collapses emergency recall or turns unknown speech into actionable events is also insufficient. This is why the table reports embedded result alongside recognition metrics.

Baseline fairness is especially important here. A generic keyword model trained on a different label mapping could look strong while avoiding the hardest part of the task: separating emergency speech from ordinary movement speech and unknown audio under rotor noise. The baseline rows above use the same three-event target and log-mel frontend, but remain preliminary offline comparisons until exact split and support parity are finalized. They therefore show useful recognizer context, not complete system alternatives. If a baseline cannot be converted to the embedded runtime, the table should still report its offline result, but mark deployment as unsupported rather than treating it as a complete system alternative.

\subsection{Control Bridge and Grounded SDK Behavior}

The fifth evaluation tests whether voice events remain mediated before they can affect the drone. The setup sends emergency, movement, unknown, silence, and background-audio events into the safety-state bridge. Any action that reaches the vehicle must pass through the gated Tello SDK command boundary. The bridge logs the previous state, event, confidence, selected boundary action, SDK dispatch decision, acknowledgement or timeout, and final state. The metrics are emergency escalation rate, movement direct-command block rate, unknown no-action rate, repeated-event suppression, SDK acknowledgement rate, and timeout handling.

This evaluation is the bridge between speech recognition and UAV safety behavior. It tests whether the voice layer can express safety-relevant events without becoming a direct flight-command channel. The current grounded/no-propeller evidence exercises one emergency event, one movement event with explicit authorization, one movement event without authorization, and three unknown events. These logs show that emergency reaches the safety-critical handling path, movement remains mediated rather than becoming a direct movement command, and unknown events are rejected to no-action or hold behavior.

The most important failure cases are not model errors alone; they are unsafe event-to-action transitions. Unknown audio should not produce movement. Movement should not bypass authorization. Emergency should not disappear silently when the bridge is active. Repeated events should not remain actionable forever. The control-boundary study turns these into explicit checks, so the paper can explain safety behavior in terms of state transitions rather than recognition accuracy alone.

\subsection{User and Geometry Study}

The sixth evaluation studies whether the interaction remains usable across different people and microphone-facing directions. Each participant is assigned a study identifier, and the recordings, embedded predictions, and offline reference predictions are stored separately for that participant. This isolation lets the evaluation report aggregate behavior while still exposing per-participant variation, which is important for a voice interface that may fail unevenly across speakers.

Each participant records three intent categories: emergency, movement, and unknown. Unknown trials include unsupported or irrelevant speech, and may also include silence or background audio, so the class represents audio that should not become a command rather than silence alone. For each intent category, the participant speaks from four directions relative to the microphone, such as front, left, right, and back. The first study keeps distance and microphone placement fixed; distance can be added as a separate robustness condition once the direction study is complete.

For each trial, the study records the participant identifier, direction, intended category, saved audio, embedded prediction, embedded confidence, offline reference prediction, reference confidence, and timing fields. The intended category is the ground truth. The offline reference model is not treated as ground truth; it is used to show how much recognition quality is lost when moving from the stronger offline recognizer to the embedded recognizer that runs in the prototype.

The primary metrics are participant-level accuracy, direction-level accuracy, emergency recall, unknown false event rate, embedded/reference disagreement rate, and speech-onset-to-event latency. Participant-level reporting is important because an average window score can hide whether the system fails for particular voices. Direction-level reporting is important because the microphone may receive very different speech and rotor-noise mixtures depending on where the person stands.

\input{figures/demo_storyboard}

The demo figure pairs the visible interaction with synchronized logs rather than standing alone. A useful demonstration shows the person speaking, the ESP32 event stream, the bridge decision, and the final visible outcome. The study then provides the controlled evidence needed to say how often that story holds across speakers and interaction geometry.

The user-study protocol separates naturalness from correctness. Participants can produce their own phrasing for each intent, and the system can also test a fixed prompt list so that acoustic and linguistic variation are not conflated. If time permits, the isolated participant records also support a user-aware adaptation experiment. In that experiment, a small number of recordings from each participant are used for fine-tuning, and held-out recordings from the same participant test whether personalization improves emergency recall, macro F1, or unknown containment. This adaptation result is reported separately from the base system so that the main evaluation does not depend on user-specific training.

This study connects the acoustic model back to the UAV platform. The shielding study is also a bridge between system design and deployment. Reporting the physical configuration alongside the acoustic metrics prevents the paper from treating rotor noise as an abstract dataset property. It keeps the evaluation tied to the UAV form factor that motivates \sys{}.
