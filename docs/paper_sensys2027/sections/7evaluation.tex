\section{Evaluation}
\label{sec:evaluation}

The evaluation asks whether a voice-driven UAV safety layer can convert speech into useful, auditable intent-state events under the constraints of a nearby drone. We separate recognition quality from runtime feasibility and from control-boundary behavior. This separation is important: a high offline score does not by itself establish a safe drone interaction, and a stable embedded runtime does not by itself establish semantic accuracy in real use.

\subsection{Recognition Quality and Robustness}

The first evaluation axis measures the recognizer as an intent-state source. The comparison should include the noise-aware anchor recognizer, the embedded deployment candidate, and baseline recognizers trained and tested under matched conditions. The primary table should report overall accuracy, macro F1, and per-state precision, recall, and F1 for movement, emergency, and unknown. Emergency recall and precision show whether safety-critical speech is preserved; movement performance shows whether ordinary interaction remains usable; unknown false accepts show whether unsupported speech is kept out of the control path.

This axis should also include the frontend and robustness studies. The frontend study compares log-mel, MFCC, and any compact embedded representation under the same split and model family. The noise robustness curve then evaluates how recognition changes as rotor-noise conditions vary. When noise is mixed offline, the curve may be indexed by SNR. When noise is collected from drone recordings, bench playback, or operating conditions, the x-axis should name the condition rather than imply a calibrated acoustic level. Speaker, distance, and language variation belong in this same recognition axis, but only as controlled robustness protocols unless labeled data are available.

\subsection{Deployment Feasibility and Response Time}

The second evaluation axis measures whether the intent-state source can run as an embedded event generator. Deployment comparison should report the constraints that matter for ESP32/TFLM: exported artifact size, quantization mode, operator compatibility, tensor-arena or memory budget, invocation success, and the model role in the system. This comparison is not only a model-quality leaderboard. It shows which recognizers can plausibly produce local safety events under the board's runtime constraints.

Response time should be measured as a path, not as a single number. The breakdown should separate audio windowing, feature extraction, inference, event serialization, host or bridge handling, and any downstream command or state-log operation. The paper should distinguish first-window latency, steady-state event period, and board-side inference time, because each supports a different claim. Runtime stability on the board supports embedded feasibility; it does not establish labeled real-world semantic accuracy.

\subsection{Safety Interaction, User Testing, and Artifacts}

The third evaluation axis connects intent-state events to the UAV interaction boundary. The bridge evaluation should replay or collect movement, emergency, unknown, silence/background, and repeated-speech cases while logging the predicted state, confidence, bridge state before the event, selected action, acknowledgement or timeout, and manual override status. The expected result is not that speech directly flies the drone; it is that voice events are converted into auditable decisions that can be held, rejected, or forwarded by a conservative policy.

The user-facing study and demo should then test whether the interaction is understandable under realistic conditions. The protocol should vary speaker, phrase wording, distance, angle, rotor-noise condition, and background condition, while recording both recognition outcomes and state-log behavior. A short demo video can illustrate the full interaction path, but the paper should treat it as qualitative system evidence unless it is paired with labeled logs and a repeatable protocol.

The artifact plan should make the evaluation reproducible. The release package should include run configurations for reported recognizers, result manifests for all tables and figures, export metadata for embedded artifacts, ESP32 runtime logs, bridge-log schemas, and scripts or notebooks that regenerate paper figures from tracked files.
