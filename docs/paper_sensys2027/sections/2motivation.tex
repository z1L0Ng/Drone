\subsection{From Voice Commands to Safety-Mediated Interaction}

For a drone operating near people, voice is most useful when it becomes a natural way to express intent while still respecting safety boundaries. A person should be able to ask the drone to move, hold, stop, or respond to a safety-critical situation without assuming a handset, cloud path, or trained operator interface is available. This paper therefore treats voice as a safety-mediated UAV interaction layer, not as a convenience wrapper around general drone piloting.

The layer should remain conservative. It maps short audio windows into a small set of interaction states and leaves final command decisions to downstream logic. Movement captures ordinary control-oriented speech but remains pending until policy supplies context. Emergency captures the safety-critical part of talking to a drone. Unknown/fallback prevents unsupported or ambiguous audio from entering the control stack.

\subsection{Why Intent-Level Modeling Fits Drone Voice Interaction}

Transcript-first processing is not the natural first step for this use case. Spoken language understanding work has shown that intent decisions can be learned directly from speech without full transcripts \cite{lugosch19_interspeech,kuo20_interspeech,mhiri20_interspeech}. For nearby drones, that direction matches the operational need: detect whether a short window contains a small set of drone-relevant intents and avoid treating every other utterance as a command.

The abstraction is deliberately narrow: \emph{emergency}, \emph{movement}, and \emph{unknown/fallback}. It is not meant to cover open-ended human-drone conversation. The narrow contract is the reason the recognizer can be connected to safety logic at all: it turns voice into a small intent-state event and makes non-matching audio explicit instead of silently folding it into a command class.

\subsection{Why Rotor Self-Noise Is Central}

Small drones create their own acoustic interference. The microphone is close to the rotors, the noise changes with operating state, and the resulting speech condition differs from quiet indoor command recognition. Prior UAV speech-interface and UAV-noise studies motivate this setting \cite{oneata19_interspeech,oneata2021multimodal,miesikowska2021uavnoise,park2023uavvehicle}.

The design therefore stays drone-centered. Cross-language, cross-speaker, and cross-platform questions are useful future context, but the core path is onboard intent-state recognition, embedded inference, and a conservative control bridge under rotor-noisy conditions.

\subsection{Why Embedded Locality Matters}

Talk-to-the-drone interaction is most useful when it remains available during the same conditions that make other interfaces fragile. A phone app may not be open, a network path may not be reliable, and a remote service can add an avoidable dependency. The voice layer therefore needs a local embedded path: audio capture, feature extraction, recognition, and event reporting should occur on or near the drone before the control bridge decides what to do.

This locality requirement turns speech recognition into a systems problem. The model cannot be chosen only by offline accuracy; it must also export to an operator set that the embedded runtime can execute, fit the memory budget, and return enough diagnostics for the bridge to audit timing and confidence. The embedded student in this paper is not presented as a better recognizer than the anchor model. It is the candidate that makes the same intent-event contract testable on the ESP32/TFLM path.

\subsection{Why a Bridge Is Part of the Design}

An intent classifier alone is not a safe drone interface. The output needs a bridge that understands vehicle state, manual override, command eligibility, and acknowledgement or timeout behavior. This is especially important because the same audio interface may see emergency utterances, ordinary movement requests, background speech, and rotor-dominated noise. The bridge is the point where intent events become auditable system behavior rather than raw classifier decisions.

The bridge also prevents the paper from overclaiming. A runtime log can show that the board produced labels and timings; it cannot show that the drone behaved safely. A dry-run dispatcher can show that event plumbing is wired; it cannot show flight behavior. The design therefore separates event generation, bridge logging, and eventual control validation.

\subsection{Design Requirements}

The system imposes four requirements. First, the voice interface must be mediated by safety states rather than exposed as direct command input. Second, the recognizer must preserve safety-critical emergency behavior while supporting ordinary movement intent under rotor-noisy conditions. Third, the embedded path must fit ESP32/TFLM operator and memory constraints so that safety events can be generated locally. Fourth, the control bridge must log state transitions and command decisions before any live-control claim is made.
