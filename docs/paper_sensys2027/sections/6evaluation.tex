\section{Evaluation}
\label{sec:evaluation}

\subsection{Evaluation Questions}

The current evidence should answer four conservative questions:
\begin{itemize}
\item \textbf{RQ1:} What completed noisy-set result is stable enough to anchor the paper narrative?
\item \textbf{RQ2:} How does the deployment-oriented \texttt{w17} branch compare with that anchor on the same reported noisy-set metrics?
\item \textbf{RQ3:} Which numbers support a model-quality claim, and which numbers only support deployment feasibility checks?
\item \textbf{RQ4:} What remains ongoing before the paper can claim completed ESP32/TFLM execution?
\end{itemize}

\subsection{Training and Configuration Provenance}

The anchor run uses \texttt{base} teacher and student profiles, reuses the \texttt{w14} clean teacher checkpoint, trains the student for up to $50$ epochs with batch size $32$, and evaluates noisy data at $-10$ dB SNR. Its class-aware augmentation enables emergency pitch and gain perturbation for the student path. These details matter because the paper should not describe \texttt{preprocess\_ext} as a generic compression or deployment run. It is the stable noise-robust training anchor.

The \texttt{w17/B\_small} run changes the model profile to \texttt{xiao\_bottleneck256\_tflm} for both teacher and student while keeping the same reported noisy-evaluation setup. That makes it useful as an early same-family deployment candidate, but its status is still ongoing because board-side \texttt{Invoke()} success has not been established in the evidence files.

\subsection{Deployment Evidence and Its Limits}

The Phase 2 artifacts provide deployment diagnostics, not a finished onboard evaluation. For the \texttt{w14/preprocess\_ext} full-integer export, the host-side TFLite profile reports input shape $[1,256,32,1]$, $165$ tensors, $104$ operators, and a largest visible runtime tensor of $524288$ bytes with shape $[1,256,32,64]$. The same profile also reports an anonymous temporary tensor of $1179648$ bytes with shape $[1,64,32,576]$, so the deployment pressure is not just flatbuffer size.

The ESP32 budget file records a current full-integer TFLM arena requirement of $8225824$ bytes, above the target range of $4194304$ to $6291456$ bytes for the local pipeline. A later \texttt{xiao\_bottleneck256} board trace allocates within a $4194304$ byte arena but fails during \texttt{Invoke()} at \texttt{Conv2D Eval}. The handoff therefore identifies \texttt{xiao\_bottleneck256\_tflm} as the next candidate because local export checks show the temporal depthwise layer as \texttt{DEPTHWISE\_CONV\_2D=1}. This is an operator-compatibility step, not final deployment evidence.

\subsection{Current Evaluation Boundary}

The paper can currently claim that \texttt{w14/preprocess\_ext} is the strongest stable noisy-set anchor among the allowed evidence paths, and that \texttt{w17/B\_small} is a close deployment-oriented candidate still under convergence. It should not claim completed ESP32/TFLM inference, final latency, final memory fit, or robust cross-platform deployment until the board-side gate records successful \texttt{AllocateTensors()}, successful \texttt{Invoke()}, and printed output labels for the selected candidate.
