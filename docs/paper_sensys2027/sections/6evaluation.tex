\section{Evaluation}
\label{sec:evaluation}

The evaluation is organized around the safety-state mediated interaction architecture rather than only the recognizer. It follows the full talk-to-the-drone stack: offline intent quality, feature representation, rotor-noise robustness, embedded deployment, board-side runtime, speaker, distance, and language variation, drone interaction behavior, and reproducible artifact packaging. This organization separates recognition evidence from systems evidence so that model accuracy is not confused with a validated control claim.

\subsection{Offline Intent Recognition Against Baselines}

The first evaluation compares the anchor recognizer against baseline recognizers on the same held-out noisy intent set. The primary metrics are overall accuracy, macro F1, and per-class precision, recall, and F1 for movement, emergency, and unknown. Emergency is reported explicitly because it is the safety-critical state, while movement and unknown show whether the recognizer preserves ordinary interaction intent and fallback behavior.

\subsection{Frontend and Representation Ablation}

The second evaluation studies the acoustic frontend used by the recognizer. The comparison holds the model family, data split, noise setup, and training schedule fixed while varying the representation, such as log-mel features, MFCC features, and any compact representation intended for embedded execution. The reported metrics are the same as the offline recognition study, with additional attention to emergency F1 and unknown false accepts.

\subsection{Embedded Deployment Comparison}

The fourth evaluation compares deployment candidates by the constraints that matter on ESP32/TFLM: exported artifact size, quantization mode, operator mix, unsupported operators, arena or tensor-memory estimate, and whether the artifact can be invoked by the runtime. This comparison is not a model-quality leaderboard. It identifies which recognizers can plausibly serve as local safety-event sources.

The embedded student exports a full-integer artifact of $780416$ bytes with \texttt{CONV\_2D=6}, \texttt{DEPTHWISE\_CONV\_2D=1}, and no grouped temporal \texttt{CONV\_2D} detected. These values support deployment feasibility for the candidate path, not labeled recognition behavior on the board.

\subsection{On-Board Runtime and Quantization Fidelity}

The fifth evaluation measures deployment-constrained safety event generation on the board: microphone capture, log-mel frontend, int8 TFLM inference, and USB CDC reporting. Runtime metrics include trigger count, success rate, drop rate, inference latency, total latency, and raw-output sanity checks. Quantization fidelity compares desktop float, desktop int8, and board-side int8 outputs for the same probe inputs.

\subsection{Speaker, Distance, and Language Robustness}

The sixth evaluation measures whether the voice layer remains usable across speakers, microphone distances, and language-specific intent phrasing. The protocol varies speaker identity, distance, angle, language or phrase set, and background condition while keeping the intent script fixed. The reported metrics are per-condition intent accuracy, emergency recall, movement accuracy, unknown false accepts, and missed-event rate.

\subsection{Drone Interaction and Bridge Behavior}

The final evaluation connects intent events to the drone interaction path. The bridge log records predicted label, confidence, bridge state before the event, selected action, command send status, acknowledgement or timeout, and manual override status. Movement, emergency, and unknown events remain distinguishable in the log, and each event produces an auditable state transition rather than an implicit command.

The interaction figure shows the end-to-end path from user speech to board event, bridge decision, and drone-side state. The experiment table includes movement, emergency, unknown, silence/background, and repeated speech-trigger cases. This evaluation is the systems evidence that connects talk-to-the-drone intent recognition to safe interaction behavior.

\subsection{Reproducible Artifacts and Extension Protocol}

The artifact package for the paper should make the safety interaction pipeline reproducible rather than only releasing a model checkpoint. The package should include run configurations for the anchor and embedded student, result manifests for reported tables, TFLite export metadata, ESP32 runtime logs, bridge-log schemas, and scripts or notebooks that regenerate the paper figures from tracked artifacts. Extension protocols should specify how new speakers, languages, drone noise recordings, or compact deployment candidates are added without changing the claim boundary.
