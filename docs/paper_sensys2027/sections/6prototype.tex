\section{Prototype}
\label{sec:prototype}

\subsection{Embedded Event Source}

The prototype turns the architecture into a local event source near the UAV. An ESP32-S3 microphone board captures audio, forms one-second analysis windows, computes log-mel features, invokes the embedded integer recognizer, and reports the resulting event to the safety-state bridge. The board is not the flight controller. Its responsibility is to make the voice layer local: speech can be heard and summarized near the drone before control-side policy considers action.

This placement is intentionally close to the acoustic source. If the microphone and recognizer depend on a phone, laptop, or remote service, the voice channel inherits the availability and latency of that external path. By putting capture and inference on the microcontroller, the prototype tests the harder system question: whether the UAV-side device can produce an intent event under the same resource limits that would constrain an onboard safety accessory.

The embedded path is organized around steady event generation. Audio capture and model execution are separated so that the system can keep accepting new windows while processing the previous one. This split matters because a one-second voice interface depends not only on the cost of a single model invocation, but also on whether the prototype can repeatedly produce one event per audio window. Section~\ref{sec:evaluation} reports both the invocation time and the observed event stream timing.

The dual-core organization follows that goal. One side of the prototype is responsible for acquiring the next audio window at a stable cadence. The other side owns feature extraction, integer inference, output formatting, and event reporting. This keeps microphone capture from being blocked by the recognizer whenever possible. It also makes timing easier to interpret: capture time, frontend time, model invocation, event reporting, and bridge delay can be recorded as separate quantities rather than collapsed into a single opaque response-time number.

The event sent by the board contains the predicted voice event, confidence, timing fields, and diagnostic output needed to interpret the decision. These fields are intentionally small. The board does not send a high-level drone command such as takeoff, land, or move. It sends the evidence required for the control boundary to decide what to do next.

\subsection{Event Reporting and Safety-State Bridge}

The prototype reports voice events to a safety-state bridge as compact timestamped intent events. The bridge attaches the current interaction state, applies the control-boundary policy, and records the outcome. This arrangement keeps the embedded board focused on local speech processing while making the control decision inspectable.

The event payload is deliberately closer to a sensor report than to a command. It includes a sequence number or timestamp, the predicted event, confidence, timing information, and status fields. The bridge adds the state that the board should not decide locally: whether manual authority is present, whether the vehicle is allowed to respond, whether a prior event is still active, and whether a vehicle-facing response completed or timed out. This split lets the prototype test the safety interaction layer without requiring the recognizer to understand the full UAV policy.

The bridge exposes the same semantics as the architecture. Emergency events are routed to safety-critical handling under policy. Movement events remain pending until the bridge decides whether the request is authorized and safe. Unknown and low-confidence events are logged and mapped to no action. This behavior lets the prototype exercise the safety-state contract without treating the recognizer as a direct controller.

The bridge also supports repeatable inspection of failure cases. If the board reports an unknown event, the bridge record shows whether it was ignored. If a movement event is produced while manual authority is absent, the bridge record shows whether the event was blocked. If an emergency event is produced, the record shows whether it entered the intended safety-critical path. These records explain the mediated response shown in the emergency demonstration because they expose the step that a speech benchmark cannot measure.

\subsection{Emergency Response Boundary}

The control side is implemented as a mediated emergency-response boundary for the laboratory demonstration in Section~\ref{sec:evaluation}. During the demonstration, the UAV continues normal operation while the embedded event source keeps processing local audio windows. When emergency speech is detected, the bridge treats the event as a safety-critical request and routes it to a configured safe landing or stopped response. Speech still does not become an arbitrary movement command; it becomes a constrained event that the boundary interprets under policy.

This setup is useful because it exposes the part of the system that a speech-only benchmark cannot see. A recognizer may correctly label a window as emergency, but the paper's claim depends on whether that event reaches a mediated response path while the drone is operating. The demonstration therefore connects local inference, event generation, boundary handling, and visible UAV behavior in one controlled scene.

A flight-facing version of \sys{} can move more of the bridge logic onto the vehicle or into a tightly integrated companion process. The current prototype is a step toward that design: it demonstrates local voice-event generation, mediated emergency response, and visible safe landing or stopped behavior while preserving a clear barrier between speech recognition and physical actuation.

This boundary is also what makes the demonstration more informative than a model label alone. The viewer can see the person speaking, the embedded recognizer continuing to run, the emergency event entering the safety-state boundary, and the UAV moving to a safe landing or stopped state. The result is evidence that the proposed interaction loop works in a constrained laboratory scene, while broader safety validation remains a separate requirement.
