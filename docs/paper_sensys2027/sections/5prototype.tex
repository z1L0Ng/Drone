\section{Prototype and Real-World Setup}
\label{sec:prototype}

This section should carry the \emph{systems} evidence that turns the model into a SenSys paper rather than a speech-model paper. The important framing choice is that the prototype is not the contribution by itself. It is one instantiation of a broader voice-safety-layer design for small nearby robots.

\subsection{Hardware and Software Stack}

The final paper needs one photo or schematic per evaluated platform and one software-path figure showing microphone capture, feature extraction, model inference, and controller dispatch. The text should specify the onboard compute target, microphone placement, inference runtime environment, and controller interface (for example, UART or MAVLink). If the implementation starts from a Tello-class drone and later expands to additional UAVs, that progression should be presented explicitly as cross-platform validation rather than as a silent change in scope.

\subsection{Decision Logic and Failsafes}

Prototype deployment should make the safety boundary explicit. Emergency predictions may use a different threshold from movement predictions, and low-confidence segments should be routed to \emph{unknown}. This section is also the right place to describe debounce logic, cooldown windows, or any two-step confirmation rules that prevent repeated false triggers.

\subsection{Real-World Test Protocol}

The real-world evaluation should not be described as an informal demo. It needs a protocol: platform type, microphone position, propeller state, speaker distance, number of speakers, command script, repetition count, and failure criteria. Even if these measurements are still being collected, the draft outline should reserve space for them now because this is one of the highest-risk gaps for a systems submission. If multiple drones are included, the protocol should make clear what transfers across platforms and what remains platform-specific.
